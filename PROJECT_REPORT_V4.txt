1. EXECUTIVE SUMMARY & MISSION STATEMENT
================================================================================
«هزار دستان» (Hezar Dastan) is an enterprise-grade, edge-native web content discovery,
RSS aggregation, and real-time news monitoring platform built specifically to execute
at the absolute edge on the Cloudflare Global Anycast Network.

The system addresses the latency, reliability, and scaling bottlenecks of traditional
centralized news aggregators by leveraging Cloudflare's serverless primitives:
- Cloudflare Workers (V8 Isolate micro-runtimes with sub-5ms cold starts)
- Cloudflare D1 (Zero-latency distributed SQLite relational database at the edge)
- Cloudflare Assets (Global edge asset distribution for static JavaScript/CSS chunks)
- Next.js 15 (App Router with React 19 and OpenNext Cloudflare adapter)

Our mission: Deliver sub-millisecond data access, zero-maintenance operational
durability, robust schema self-healing, complete Persian RTL user experience,
and strict security isolation across all deployments.

4. RUNTIME EXECUTION ENVIRONMENT & WORKERD COMPATIBILITY
================================================================================
Cloudflare Workers execute within V8 Isolates rather than full Node.js virtual
machines. This imposes strict architectural constraints:

1. Filesystem (fs) Isolation:
   - Workers have no writable local filesystem.
   - All persistence must flow through Cloudflare D1, KV, or R2.
   - Codebase strictly avoids `fs.writeFile` or local file caching in runtime paths.

2. Process & Threading Model:
   - `child_process` and native C++ binary addons are forbidden.
   - Node compatibility is provided via `compatibility_flags = ["nodejs_compat"]`.

3. Asynchronous Context & Lifecycle:
   - Request handlers must complete within CPU time limits.
   - Database queries utilize native asynchronous bindings (`await db.prepare()`).
   - Context is safely retrieved using `@opennextjs/cloudflare`'s `getCloudflareContext({ async: true })`.

4. Isolate Cold Start Optimization:
   - Lazy initialization is used for all external clients.
   - Global scope state is kept minimal, relying on lightweight in-memory cache
     flags (`isSchemaEnsured`) to avoid redundant initialization.

--- Data Definition Language (DDL) ---

[TABLE 1: `sources`]
```sql
CREATE TABLE IF NOT EXISTS sources (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    slug TEXT NOT NULL UNIQUE,
    base_url TEXT NOT NULL,
    feed_url TEXT,
    discovery_type TEXT NOT NULL DEFAULT 'rss',
    polling_interval_minutes INTEGER NOT NULL DEFAULT 15,
    is_active INTEGER NOT NULL DEFAULT 1,
    last_polled_at TEXT,
    health_status TEXT NOT NULL DEFAULT 'healthy',
    consecutive_failures INTEGER NOT NULL DEFAULT 0,
    articles_count INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX IF NOT EXISTS idx_sources_slug ON sources(slug);
CREATE INDEX IF NOT EXISTS idx_sources_is_active ON sources(is_active);
```

[TABLE 2: `articles`]
```sql
CREATE TABLE IF NOT EXISTS articles (
    id TEXT PRIMARY KEY,
    source_id TEXT NOT NULL,
    source_name TEXT NOT NULL,
    title TEXT NOT NULL,
    url TEXT NOT NULL UNIQUE,
    summary TEXT,
    content_text TEXT,
    content_html TEXT,
    published_at TEXT,
    discovered_at TEXT NOT NULL DEFAULT (datetime('now')),
    processing_status TEXT NOT NULL DEFAULT 'discovered',
    tags TEXT DEFAULT '[]',
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at TEXT NOT NULL DEFAULT (datetime('now')),
    FOREIGN KEY (source_id) REFERENCES sources(id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_articles_source_id ON articles(source_id);
CREATE INDEX IF NOT EXISTS idx_articles_url ON articles(url);
CREATE INDEX IF NOT EXISTS idx_articles_processing_status ON articles(processing_status);
CREATE INDEX IF NOT EXISTS idx_articles_discovered_at ON articles(discovered_at DESC);
```

--- Self-Healing Schema Verification Pattern ---
To prevent unhandled `no such table` exceptions during cold starts or initial
deployments, `lib/db.ts` executes statements individually through `ensureSchema()`:
- Statements are maintained as an array of discrete single SQL commands.
- `fetchSources()` and `fetchArticles()` intercept any D1 SQLite error, invoke
  `ensureSchema(db)`, and seamlessly retry the transaction before returning.

  {
    "name": "Cointelegraph",

    "feedUrl": "https://cointelegraph.com/rss",
    "discoveryType": "rss",
    "pollingIntervalMinutes": 15,

- Validation Rules:
  * `name` (required, non-empty string)

  * `feedUrl` (optional, valid HTTP/HTTPS URL)
  * `discoveryType` (must match 'rss' | 'sitemap' | 'html' | 'telegram')
  * `slug` is automatically generated if omitted.
- Response Code: 201 Created
- Response Body:
  {
    "success": true,
    "data": SourceObject,
    "source": SourceObject
  }

--------------------------------------------------------------------------------

- Parameters: `id` (source UUID or slug-based identifier)

10. CONTENT DISCOVERY & RSS AGGREGATION ENGINE PIPELINE
================================================================================
The content discovery engine operates through a multi-stage lifecycle:

Stage 1: Source Discovery & Registration
  - Sources are registered via UI modal, API endpoint, or direct D1 SQL migrations.
  - Supports multiple discovery types:
    * `rss`      : Standard RSS 2.0 / Atom XML feeds (e.g., Cointelegraph RSS).
    * `sitemap`  : XML Sitemap inspection for bulk URL indexing.
    * `html`     : Semantic HTML scraping with CSS selectors.
    * `telegram` : Public channel message parsing.

Stage 2: Edge Polling & Polling Interval Enforcement
  - Each source defines a `polling_interval_minutes` (5, 15, 30, 60 min).
  - The worker evaluates `last_polled_at + interval` against `datetime('now')`.

Stage 3: Parsing, Deduplication & Storage
  - Incoming articles are identified by their canonical URL (`url` column has a UNIQUE constraint).
  - Conflict resolution: Existing URLs are skipped or updated without data duplication.
  - Cascade relations: Deleting a source automatically cleans up all associated articles.

11. SECURITY ENGINEERING, VULNERABILITY MITIGATION & DATA PROTECTION
================================================================================
1. Parameterized SQL (SQL Injection Defense):
   - Every single SQL statement across `lib/db.ts` uses bound parameters:
     `db.prepare('INSERT INTO sources (...) VALUES (?, ?, ...)').bind(...)`
   - Zero raw string concatenations exist in database execution paths.

2. XSS (Cross-Site Scripting) Defense:
   - React's JSX auto-escaping renders all user-provided strings safely.
   - HTML previews are strictly sanitized or rendered as plain text strings.

3. Secret Protection:
   - Zero API keys, passwords, or cloud credentials are hardcoded.
   - Cloudflare D1 access is granted internally via Worker Bindings, not external connection strings.

4. Open Redirect & SSRF Precautions:
   - Source URLs must validate against standard HTTP/HTTPS protocols.
   - External links on the frontend utilize `rel="noopener noreferrer"`.

15. CHRONOLOGY OF RESOLVED CRITICAL ISSUES & ROOT CAUSE ANALYSIS
================================================================================

1. Issue: `UnknownLockfileVersion: failed to parse lockfile` during Cloudflare CI
   - Root Cause: A Bun lockfile v2 was committed while the Cloudflare remote build
     system was running Bun v1.2.
   - Resolution: Removed `bun.lock`, standardized on `package-lock.json` with npm 10+,
     and added `bun.lock*` to `.gitignore`.

2. Issue: `D1_EXEC_ERROR: Error in line 1: CREATE TABLE IF NOT EXISTS sources (: incomplete input`
   - Root Cause: Multi-line, multi-statement DDL string passed into `db.exec()` failed
     SQLite parsing in D1.
   - Resolution: Split schema statements into discrete single SQL commands and executed
     each sequentially with `db.prepare(sql).run()`.

3. Issue: Downstream `no such table: sources` / `articles`
   - Root Cause: The schema creation failure left the D1 database tables uninitialized.
   - Resolution: Implemented automatic self-healing schema retry inside `fetchSources()`
     and `fetchArticles()`.

4. Issue: Wrangler warning regarding `preview_urls`
   - Root Cause: Cloudflare introduced default preview URL settings for `workers.dev`.
   - Resolution: Added explicit `preview_urls = false` in `wrangler.toml`.

5. Issue: API / UI Payload Key Discrepancy
   - Root Cause: UI expected both `data` and domain arrays (`sources`/`articles`).
   - Resolution: Standardized API routes to return dual format keys.
